## はじめに

教科書の最小RISC-VコアをKV260上で育ててきたシリーズです。これまでに [完全RV32I化してOS(KOZOS流)を載せ](https://zenn.dev/douhaku1115/articles/riscv-kv260-kozos)、RV32M(乗除算)・分岐予測(BTB+gshare)を足し、[2コアSMP](https://zenn.dev/douhaku1115/articles/riscv-kv260-smp) まで動かしました。

今回は **RV32C（圧縮命令拡張）** を実装します。結果から言うと：

| プログラム | rv32i(m) | rv32imc | 削減 |
|---|---|---|---|
| Σ0..100 | 17語 | **12語** | 29% |
| KOZOSシェル一式（OS丸ごと） | 2167語 | **1509語** | **30.4%** |

**同じCソースをコンパイルオプション1つ（`-march=rv32imc`）でコードサイズ30%減**。教科書通りの圧縮率が自作コアでも出ました。もちろん実機KV260の100MHzで、圧縮されたOS（割込み・コンテキストスイッチ・対話シェル込み）が完全動作します。

実装のキモは2つ——**16bit→32bit展開器**（即値のスクランブル解き）と、**「32bit命令がワード境界をまたぐ」問題**です。特に後者は教科書だと「フェッチバッファが要る」ところを、**常に連続2ワード読む**方式でバッファ無しに解決できたので、そこを詳しめに書きます。

ソース一式: https://github.com/douhaku1115/kv260 の `riscv_kv260/`（`src/main_vio_rvc.v`）

## RV32Cとは：新機能ゼロの拡張

RV32Iの命令は32bit固定長ですが、RV32Cは**よく使う命令に16bitの短い符号化を追加**します。

```
addi sp, sp, -16   → 32bit
c.addi sp, -16     → 16bit(同じ意味)
```

重要なのは「**C命令はすべて既存32bit命令の短縮形**」だということ。つまり**デコード時に32bitへ展開してしまえば、パイプライン本体（ALU・レジスタ・フォワーディング・割込み）は一切変更不要**です。実際、今回の実装でパイプラインの実行部は1行も変えていません。

なぜ縮むかというと、実際のコードは統計的に偏っているからです：
- よく使うレジスタは8個（s0-s1, a0-a5）に集中 → レジスタ指定5bit→3bit
- 即値は小さい値が大半 → 即値フィールド6bit程度で足りる
- `addi`/`lw`/`sw`/`mv`/分岐/ジャンプが頻出

この「頻出の形」だけ16bit化し、収まらないものは32bitのまま。**16bitと32bitが混在**するバイナリになります。命令の下位2bitが`11`なら32bit、それ以外なら16bitと判別できます。

## 展開器：即値スクランブルとの戦い

展開器は約25命令ぶんの場合分けです。ロジック自体は単純ですが、**C形式の即値はビット配置がバラバラ**（符号化効率のためフィールドを再利用している）で、ここが最大の敷居でした。例えば `c.addi4spn` の即値：

```verilog
// nzuimm[9:6]=ci[10:7], [5:4]=ci[12:11], [3]=ci[5], [2]=ci[6] (4バイト倍数)
wire [11:0] i_4spn = {2'b00, w_ci[10:7], w_ci[12:11], w_ci[5], w_ci[6], 2'b00};
```

`c.j`/`c.jal` のオフセットはさらに複雑で、11bitが `[11|4|9:8|10|6|7|3:1|5]` の順に散っています。1bitでも間違えるとジャンプ先が壊れるので、形式ごとに`wire`で名前を付けて組み立て、gccの逆アセンブルと突き合わせて検証しました。

```verilog
case ({w_ci[1:0], w_ci[15:13]})
  5'b01_000: w_ir = {i_imm6, rd, 3'b000, rd, 7'h13};   // c.addi → addi rd,rd,imm
  5'b01_101: w_ir = {j_fld, 5'd0, 7'h6F};              // c.j    → jal x0,imm
  ...
```

## フェッチ：ワード境界またぎ問題

RV32C最大の構造的問題はここです。IMEMは32bit幅なのに、命令が16bit単位で始まるようになるため、**16bit命令の次に来る32bit命令が2つのワードにまたがる**ことがあります。

```
アドレス:  0x08   0x0a       0x0e
命令:      c.jal  lui(32bit)  sw(32bit)
                  ~~~~~~~~~~ ← word0の上位16bit + word1の下位16bitにまたがる！
```

教科書的な解法は「前半16bitを保持するフェッチバッファ（状態機械）」ですが、パイプラインのフラッシュ・ストールとの絡みでバグの温床になります。

今回は**力技だけどシンプルな方法**を採りました：**IMEMに読みポートを1本足して、毎サイクル「現ワード＋次ワード」の2つを常に読む**。

```verilog
assign w_insn    = mem[pc[13:2]];        // 現ワード
assign w_insn_hi = mem[pc[13:2]+1];      // 次ワード(またぎ用)

// pcから始まる32bitを組合せで組み立て(pc[1]=1なら境界またぎ)
wire [31:0] w_raw = pc[1] ? {w_insn_hi[15:0], w_insn[31:16]} : w_insn;
wire w_cmp = (w_raw[1:0] != 2'b11);       // 16bit圧縮命令?
assign w_ir  = w_cmp ? w_exp : w_raw;     // 圧縮なら展開器の出力
assign w_npc = pc + (w_cmp ? 2 : 4);      // 次PCは+2 or +4
```

これで**状態機械ゼロ・ストールゼロ**でまたぎが解決します。コストはIMEMの読みポート1本（分散RAMの複製）ですが、100MHzでは問題になりませんでした（WNS +0.589ns）。

## PC制御：+2の伝搬

PCが2バイト単位になると、随所の「+4」決め打ちを直す必要があります。

- **逐次PC**: `pc + (圧縮?2:4)` ← フェッチで判定
- **リンク値**: `c.jal`/`c.jalr` の戻りアドレスは `pc+2`（32bit版は`pc+4`）
- **分岐の真の次PC**: 分岐予測のミス判定に使う「分岐が不成立なら次は`pc+4`」も、圧縮分岐（`c.beqz`等）では`pc+2`

そこで「この命令は圧縮だったか」フラグをフェッチ→デコード→実行(P2)段までパイプラインで伝搬し、リンク値とミス判定を補正しました。分岐・ジャンプの**飛び先**については、B/J形式のオフセットがもともと2の倍数（bit0暗黙0）なので、実は無修正で2バイト境界に飛べます。

## ハマりどころ：分岐予測のBTBが「別の命令」に誤ヒットする

一番危なかったバグ（設計段階で気づけた）はこれです。

このコアの分岐予測は BTB（分岐先キャッシュ）をフェッチ段で引き、ヒットすれば投機的にリダイレクトします。BTBのタグは `pc[31:8]`、インデックスは `pc[7:2]` でした——つまり **`pc[1]` をどこにも見ていない**。

RV32I時代は全命令4バイト境界なのでこれで一意でしたが、RV32Cでは **2バイト違いの2命令（例: 0x100と0x102）が同じエントリに載り、タグも一致**してしまいます。すると：

1. 0x102 の分岐がBTBに登録される
2. 0x100 の**分岐ではない**命令をフェッチしたとき、BTBがヒットして投機リダイレクト
3. ミス予測の検出は「P2に**分岐**があるとき」しか働かないので、**誤ったリダイレクトが検出されないまま実行が壊れる**

対策は**BTBタグに `pc[1]` を追加**（24bit→25bit）。予測器は「外れても検出・回復できる」のが基本ですが、**非分岐命令への誤ヒットは回復機構の外**にある、というのが教訓です。gshare（方向予測）の方はインデックスが濁っても性能が落ちるだけなので、そのままにしました。

## 検証と結果

段階的に検証しました。

1. **回帰**: 従来のrv32i（非圧縮）バイナリがそのまま動くこと（C命令が来なければ展開器は素通し）→ KOZOSシェル `sum`=5050 ✓
2. **圧縮Σ**: `-march=rv32imc` でコンパイルしたΣ0..100。逆アセンブルを見ると、16bit命令が10個、**境界をまたぐ32bit命令**も複数 → 結果0x13BA ✓
3. **圧縮フルOS**: KOZOSシェル一式をrv32imcでビルド（30.4%減）。割込み・コンテキストスイッチ・プリエンプティブなワーカー・乗算・ブートローダ（`load`で送ったfib=610）まで全部動作 ✓

実機KV260でも：

```
KOZOS> sum
5050
KOZOS> calc 6 * 7
42
KOZOS> ps
 t1 READY pri=1 cnt=782936   <- 圧縮コードのワーカーが100MHzで並行カウント
 t2 READY pri=1 cnt=309658
 t3 READY pri=1 cnt=225377
```

**16bit/32bit混在・境界またぎ込みの圧縮命令OSが、実機で完全動作**しました。

## おわりに

RV32Cは「新しい機能が何も増えないのに、実装するとアーキテクチャの理解が一段深まる」拡張でした。

- 展開器を書くと、**C命令が何の短縮形か**＝実コードの統計的な偏りが体感できる
- フェッチまたぎ問題で、**固定長命令がいかにフェッチを単純にしていたか**が分かる
- BTBの誤ヒットで、**「予測は外れてもよいが、嘘の予測対象はダメ」**という予測器設計の原則に当たる

これで自作コアは **RV32IMC＋分岐予測**になりました。組み込み向けRISC-Vコア（SiFive E2xやESP32-C3など）がほぼ例外なくCを積んでいる理由——フラッシュ/ROM容量への直接効果——を、30.4%という数字で確認できたのが今回の収穫です。
