## はじめに

前回、[「RISC-Vで学ぶコンピュータアーキテクチャ」のパイプラインプロセッサをKV260で動かす](https://zenn.dev/douhaku1115/articles/riscv-kv260-pipeline) という記事で、教科書のVerilogプロセッサをXilinx Kria KV260上で動かしました。

今回はその続きとして、**そのRISC-Vコアを拡張して自作OS（[KOZOS](https://kozos.jp/kozos/) 流のマルチタスクOS）を載せ、実機でシリアル対話シェルまで動かす**ところまで進めました。最終的にはこんな感じで、自作CPU上の自作OSにコマンドを打って操作できます。

```
KOZOS console
KOZOS> run
spawned t1
KOZOS> ps
 t0 RUN   cnt=0
 t1 SLEEP cnt=695531     <- 100MHzで裏で回り続けるワーカースレッド
 t5 READY cnt=0
KOZOS> peek 30008
0x1cd3e49b              <- タイマの値。打つたびに変わる
```

教科書の最小コアから、**例外・タイマ割込み・コンテキストスイッチ・スケジューラ・sleep・セマフォ・メッセージング・UARTコンソール**までを一段ずつ積み上げた記録です。ハマりどころも正直に書きます。

ソース一式: https://github.com/douhaku1115/kv260 の `riscv_kv260/`

## 全体像

まず完成形の構造から。KV260 は Zynq UltraScale+ MPSoC で、ARM側(PS)とFPGA側(PL)があります。

```
┌──────────────────────────────────────────────────────┐
│ KV260 (Zynq UltraScale+ MPSoC)                        │
│  PS(ARM/PetaLinux)  ──pl_clk0(100MHz)──▶  PL(FPGA)    │
│  ・SDから起動                              ・自作RISC-V  │
│  ・fpgautilでbit投入                        ・KOZOS     │
└──────────────────────────────────────────────────────┘
        PMOD(UART) ─▶ USB-TTLアダプタ ─▶ ホストPC(tio)で対話
```

PS(Linux)は**クロック供給とビットストリーム投入だけ**を担当し、RISC-V+KOZOSはPL内で自己完結しています。

PL内の自作コアはこう積み上げました（各段は実機VIOまたはシリアルで動作確認済み）。

| 段 | 追加したもの | 確認 |
|---|---|---|
| 前回 | 5段パイプライン RISC-V（教科書の最小構成） | Σ0..100=5050 |
| ② | CSR + 例外（`ecall`/`mret`） | mcause=11 |
| ③ | **完全RV32I** + gccツールチェーンフロー | gccのCが動く |
| ④ | マシンタイマ割込み | 5回割込み |
| ⑤ | KOZOS（コンテキストスイッチ〜メッセージング） | 対話シェル |

## ② CSR と例外（ecall / mret）

OSには「システムコール」と「例外処理」が要ります。RISC-Vでは特権レジスタ(CSR)と `ecall`/`mret` 命令で実現します。

教科書コアにはCSRが無いので追加しました。最小構成として:

- CSR: `mtvec`(例外ベクタ) / `mepc`(戻り先PC) / `mcause`(要因) / `mscratch`
- 命令: `csrrw` / `csrrs` / `ecall` / `mret`

トラップは、既存の分岐解決と同じ **EX段（P2）** に相乗りさせるのがラクでした。分岐ミス時にパイプラインをフラッシュする仕組みがすでにあるので、`ecall` でも同じ経路で「若い命令を潰して `mtvec` へ飛ぶ」を実現できます。

```verilog
// ecall検出時: mepc<-PC, mcause<-11, PC<-mtvec, パイプラインflush
wire w_redir = w_miss | w_trap_e | w_trap_r;  // 分岐ミス | ecall | mret
assign w_pcin = w_trap_e ? csr_mtvec :
                w_trap_r ? csr_mepc  : ...;
```

`ecall`→ハンドラ→`mret` で元の場所に戻る往復を、手アセンブルのプログラムで確認しました。

## ③ 完全RV32I化 + gccフロー

ここが地味に一番大変でした。教科書コアの ALU は**実質「加算」だけ**、分岐も `bne` だけの最小構成です。これでは gcc が吐くコードは動きません（`int main(){return 5050;}` ですら関数プロローグの `sw/lw`、復帰の `jalr`、定数生成の `lui` を使う）。

そこで **RV32I（base整数命令セット）を全部実装**しました。

- ALU全部: `add/sub/sll/slt/sltu/xor/srl/sra/or/and`（＋即値版）
- 全分岐: `beq/bne/blt/bge/bltu/bgeu`
- ジャンプ: `jal` / `jalr`
- 上位即値: `lui` / `auipc`
- ロード/ストア全幅: `lb/lh/lw/lbu/lhu` / `sb/sh/sw`

### ハマり① `sra` が論理シフトになる

算術右シフト `sra` が論理シフトになるバグに遭遇。原因はVerilogの古典的な罠でした。

```verilog
// NG: 三項で符号付き>>>と符号無し>>を混ぜると、式全体が符号無し扱いになり
//     >>> が論理シフト化する
w_out = w_sra ? ($signed(w_in1) >>> sh) : (w_in1 >> sh);
```

シフトを別々のwireに分離して解決しました。

```verilog
wire [31:0] w_srl = w_in1 >> sh;              // 論理右
wire [31:0] w_sar = $signed(w_in1) >>> sh;    // 算術右(自己決定で符号付き)
...
w_out = w_sra ? w_sar : w_srl;
```

### ハマり② ロードアドレス計算が funct3 で壊れる

`sw a0,0(t0)` のアドレスが `0` になる、というバグ。ALUの演算をそのまま命令の `funct3` で選んでいたため、**`sw`のfunct3=010がALUではSLTになって**アドレス計算（本来は加算）が壊れていました。

ALUがfunct3を使うのは `OP`(R形式)と`OP-IMM`だけ。ロード/ストア/`lui`/`auipc`/`jal`/`jalr` はアドレス・リンク計算なので**常に加算**に強制して解決。

### gccフロー

これでC言語が動くので、ツールチェーンフローを整えました（Vitis同梱の `riscv64-unknown-elf-gcc`）。

```
C/asm ─gcc(-march=rv32i)→ ELF ─objcopy(.text)→ 命令メモリ用include ─Vivado合成→ IMEMに焼込み
```

`gcc` でコンパイルした `for(i=1;i<=100;i++)s+=i;` が実機で 5050 を返したときは感動しました。手アセンブル卒業です。

検証は「gcc出力を**ホストgccの実行結果と突き合わせ**る」方式にしました。最適化バリア(`asm volatile("":"+r"(x))`)で全命令を強制発行させ、ホストと同じ値が出るかで全ALU/シフト/比較/バイト・ハーフメモリを一気に確認。

## ④ マシンタイマ割込み

プリエンプション（時間でタスクを強制切替）の心臓部。RISC-Vのマシンタイマを実装しました。

- CSR: `mstatus`(MIE/MPIE) / `mie`(MTIE) / `mip`(MTIP)
- メモリマップド64bitタイマ: `mtime`(自走) / `mtimecmp`(比較値)
- `mtime >= mtimecmp` かつ `MIE & MTIE` で割込み → `mepc`退避・`mcause=0x80000007`・`PC<-mtvec`

`gcc` の `__attribute__((interrupt("machine")))` でハンドラを書けるので、C言語で割込みハンドラを書いて、周期的にtickが入るのを確認しました。

## ⑤ KOZOS：コンテキストスイッチとスケジューラ

いよいよOS本体。KOZOSは「[12ステップで作る組込みOS自作入門](https://kozos.jp/kozos/)」の教材OSで、H8マイコン版が有名です。その考え方をRISC-Vに移植しました。

### コンテキストスイッチ（アセンブリ）

トラップ入口で**全GPR(x1-x31)とmepcを現スレッドのスタックに退避**し、スケジューラが選んだ次スレッドのスタックから復元して `mret` します。

```asm
trap_entry:
    addi sp, sp, -128
    sw x1, 1*4(sp)     # x1,x3..x31 を退避(x2=spは除く)
    ...
    csrr t0, mepc
    csrr t1, mcause
    bltz t1, 1f        # 割込みならmepc+4しない(命令を再実行)
    addi t0, t0, 4     # 例外(ecall)は次命令へ
1:  sw t0, 0(sp)
    mv  a0, sp
    call ksched        # C: 現spを保存し次スレッドのspを返す
    mv  sp, a0
    ... 全レジスタ復元 ...
    mret
```

スレッド生成は「**スタックに偽の初期コンテキストを作り、初回の復元でスレッド関数へ飛ばす**」という定番手法です。

### スケジューラ（C）

ラウンドロビン。スレッドの状態（READY/SLEEP/BLOCK/DEAD）を持ち、タイマ割込みで切り替えます。まず **協調(yield)** で2スレッドが交互に動くのを確認し、次に **プリエンプティブ**（yield無しで `for(;;)` を回すスレッドをタイマだけで強制切替）に発展させました。

```
seq: 1 → 12 → 121 → 1212 → 12121 → 121212
```

2スレッドが共有変数に交互に桁を追加し、`121212` になれば厳密交互＝コンテキストスイッチ成立、という観測方法で確認しました。

### ハマり③ 割込みストーム

プリエンプティブ化＋sleepを入れたら、スレッドが1命令も進まなくなりました。原因は **割込みハンドラのコスト＞タイマ間隔**。

割込みハンドラ（32レジスタの退避/復元＋スケジューラ、分岐ミスペナルティ込みで約130サイクル）が、タイマ間隔より長いと、**ハンドラ実行中に `mtime` が次の `mtimecmp` を追い越し、戻った瞬間にまた割込み**が入り続けます。タイマ間隔を十分大きく（1000サイクル）取って解決しました。

## ⑤ KOZOSのサービス：sleep / セマフォ / メッセージング

カーネルの上に、KOZOSらしいサービスを載せました。

- **sleep(n)**: n ティック休止して他スレッドにCPUを譲る。全スレッドが休止中なら idle スレッドが回ってティックを進める。
- **セマフォ**: `wait`/`signal`。バイナリセマフォ2つでping-pongを強制し、タイミングに依らず厳密交互を実現。
- **メッセージング**: `send`/`recv`。メールボックス（リングバッファ）＋ブロック。producer→consumer で値を渡す。`recv` は戻り値(a0)で受信値を返し、`send` がブロック中の `recv` を起こす。

いずれも「時間ではなくイベントで待つ(BLOCKED)」という状態を導入する練習になりました。

## ⑤ UARTコンソールと対話シェル

ここまで結果は VIO(JTAG)でしか見られませんでしたが、**UART送受信**を付けて対話できるようにしました。

- コアにメモリマップドUART（TX/RX、それぞれ16段FIFO）を追加
- PMODから USB-TTLアダプタ経由でホストPCへ（`tx=B11(J2-10)`、`rx=D11(J2-9)`、115200 8N1）

### ハマり④ 文字列リテラルが読めない

シェルで `str_eq(line,"sum")` が一致しない。原因は、**文字列リテラル(.rodata)が `.text`＝命令メモリ(IMEM)に置かれるのに、ロード命令はデータメモリ(DMEM)しか読めない**こと。文字列比較がゴミとの比較になっていました。

IMEMにデータ読み出しポートを足し、text/rodata領域へのロードはIMEMから読むようにして解決。これで全プログラムで文字列リテラルが使えるようになりました。

### 対話シェル + カーネル統合

最後に、シェル自身を**1つのKOZOSスレッド**として走らせ、プリエンプティブ・カーネルと統合しました。コマンドで生きたOSを操作できます。

| コマンド | 動作 |
|---|---|
| `run` | ワーカースレッドを動的起動 |
| `ps` | スレッド一覧（id/状態/カウンタ） |
| `kill <id>` | スレッド終了 |
| `tick` | システムtick |
| `peek <hex>` / `poke <hex> <hex>` | メモリ/MMIO 直読み書き |
| `sum` / `echo` / `help` | おまけ |

実機でこう動きます。ワーカーのカウンタが100MHzで裏で回り続け、`ps` を打つたびに増えていきます。

```
KOZOS> run
spawned t1
KOZOS> run
spawned t2
KOZOS> ps
 t0 RUN   cnt=0
 t1 SLEEP cnt=695531
 t2 SLEEP cnt=384046
 t5 READY cnt=0
KOZOS> poke 40000 5a     <- UART送信レジスタに 'Z'(0x5a) を書く
Zok
```

`peek 30008`（mtimeの下位）を連打すると値が回り続け、タイマが動いているのが目で見えます。自作CPU上の自作OSを、シリアル越しに触っている実感があります。

## まとめ

教科書の最小RISC-Vコアから始めて、

1. CSR/例外を足し、
2. 完全RV32I化してgccのCを動かし、
3. タイマ割込みでプリエンプションを実現し、
4. コンテキストスイッチ＋スケジューラでマルチタスクを作り、
5. sleep/セマフォ/メッセージングを載せ、
6. UARTコンソールで対話できるようにする、

というところまで、**設計→シミュレーション→KV260実機→公開**を一段ずつ積み上げました。

CPUを自作すると「命令が動く」で終わりがちですが、その上にOSを載せて対話シェルまで持っていくと、**ハードとソフトが地続きになっている感覚**が得られて面白いです。特に、rodataが読めない/割込みストーム/シフトの符号といった「レイヤーをまたいだバグ」に出会えるのが自作の醍醐味でした。
