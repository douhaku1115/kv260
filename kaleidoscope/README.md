# 万華鏡を KV260 の FPGA で動かす

ブラウザで動いている「オイル万華鏡」と同じ映像を、Kria KV260 の PL で毎画素計算して
HDMI に出す。


WebGL2 / 単一 HTML / 1592 行。ブラウザで開くだけで動く。

## 何をしているか

万華鏡は「のぞき穴から出た光線を、三角形に並べた3枚の鏡で反射させながら奥へ進め、
セル面（オイルとピースが入った部屋）に届いた位置の色を見る」もの。

鏡は筒の軸と平行なので、光線追跡は**断面の 2D 問題**に落ちる。
これを 1 画素 1 クロックの 16 段パイプラインにして PL に載せた。

```
画素座標 ──> slope = sp/focal ──> p = slope*Z_MIRROR ──┐
                                                        │
      ┌─────────────────────────────────────────────────┘
      v
  [ scope_stage x16 ]   1段 = 3枚の壁との交差判定 + 反射
      │
      v
  c = p / TUBE_R ──> cell_mem (セル画像) ──> 減光 ──> 周辺減光 ──> HDMI
```

### パイプラインを軽くした2つの工夫

**1. 光線を正規化しない**

`p(z) = slope * z` なので、媒介変数に奥行き z をそのまま使える。
参照実装の

```glsl
float sl = length(slope);
vec2 dir = slope / sl;
float remain = sl * (Z_CELL - Z_MIRROR);
```

は、`dir = slope`（正規化しない）、`remain = Z_CELL - Z_MIRROR`（**全画素で同じ定数**）
と完全に等価。平方根も正規化の除算も要らなくなる。

**2. 一番近い壁を選ぶのに除算を使わない**

```
t_w = a_w / dn_w        a_w = wd_w - dot(p, n_w),  dn_w = dot(dir, n_w) > 0
t_i < t_j  ⟺  a_i * dn_j < a_j * dn_i
```

掛け算の大小比較で最小の壁を決め、**選ばれた1枚だけ除算**する。
残り距離との比較（`t < remain ⟺ a < remain * dn`）も同じ手で除算不要。
結果、1段あたり除算は1個。

除算器も IP を使わず、逆数表（512エントリ）+ ニュートン1回で組んだ（`divq.v`）。

## 数の形式（固定小数点）

| 量 | 形式 | 幅 | 範囲 / 分解能 |
|---|---|---|---|
| p, dir | Q3.15 | 18bit 符号付き | ±4 / 3.1e-5 cm |
| 法線 n | Q2.16 | 18bit 符号付き | \|n\| = 1 |
| a, wd | Q4.14 | 18bit 符号付き | ±8 |
| dn | Q3.15 | 18bit 符号付き | |
| q, remain | Q6.14 | 20bit 符号なし | 0〜11.9 |

18bit に揃えてあるので、掛け算はすべて DSP48E2 1個に収まる。

浮動小数点の正解（`tools/ref_scope.py`）と比べて **平均誤差 0.32/255、反射回数の不一致 0.14%**。

## 筒の寸法

```
TUBE_R   = 2.25 cm   筒の内側の半径 = セルの半径
Z_MIRROR = 0.3  cm   のぞき穴 → 鏡の手前の端
Z_CELL   = 12.2 cm   のぞき穴 → セル手前層
鏡の外接円 R = 2.05 cm、頂角 180/ポイント数
```

反射回数はポイント数8・傾き0で最大16回（実測、`tools/refl_hist.py`）。
だから K=16 で足りる。平均は 7.5 回。

## 作り方

### 1. シミュレーションで絵を確かめる

```bash
python tools/gen_hex.py           # 表とテストセル画像を作る
cp rtl/cell_real.hex rtl/cell_init.hex   # 本物のセル画像を使う場合
bash sim/run_sim.sh               # xsim で 1 フレーム回す (約6分)
python tools/cmp_rtl.py           # モデルと突き合わせて PNG を出す
```

`sim/rtl_scope.png` が RTL の出力、`sim/model_cell256.png` がモデルの出力。
差が大きい画素は `sim/diff.png` に赤で出る。

### 2. 合成

```
E:\vivado\2025.2\Vivado\bin\vivado.bat -mode batch -source E:/fpga/kria260/kaleidoscope/vivado.tcl
```

`project_1/design_1_wrapper.xsa` ができる。

### 3. 実機（ベアメタル Vitis）

SD カードは抜いておく。ただしこの KV260 は **QSPI にブートイメージがあるので
SD を抜いてもフルブートする**。それを前提にした手順が下の 8〜11。

1. Vitis Unified IDE を起動、ワークスペース `E:\Xilinx\project_vitis\ws_kv260_kaleido` を新規作成
2. Platform Component を作成し、`project_1/design_1_wrapper.xsa` を指定
3. Application Component `kaleido_app` を作成、Platform に紐付け
4. `vitis_src/main.c` をワークスペースの `src/` に **ファイルコピーで**同期（IDE の Import だけでは元ファイルの変更が反映されない）
5. `UserConfig.cmake` に `"../main.c"` の行が混入していたら削除。`USER_LINK_LIBRARIES` に `m` を追加（DP ドライバが `nearbyint` を使う）
6. Platform → Build、Application → Build
7. KV260 の電源を入れ、USB-UART のシリアル端末（115200）を開く
8. シリアルに `ZynqMP>` の U-Boot プロンプトが出たら、そのまま待つ
   （この個体は QSPI ブートなので SD を抜いてもここまで進む）
9. Debug Configuration は **Board Initialization = FSBL** のままでよい
   （映像系の成功例 pong / chip8 / rect / tetris はすべて FSBL）。
   駄目なら TCL に切り替える
10. Debug 実行 → `main` で停止 → **Resume**
11. HDMI モニタに映像、UART に `KV260 Kaleidoscope Start` が出る

`Failed to detect FSBL exit status using symbol: XFsbl_Exit` は警告。
シリアルに出力が出ていればアプリは動いている。

ワークスペースを再利用すると `_ide/bitstream/` が自動更新されない。
`.bit` を手で置き換えるか、ワークスペースを作り直すこと。

## 操作

KV260 にはキーボードもマウスも標準では無い。既につながっている USB-UART を
入力に使う。Tera Term（115200）でキーを打つと設定が変わる。
**JIS 配列で Shift が要るキー（`<` `>` `+` `=`）は使わない。**

| キー | 動き |
|---|---|
| `q` `w` | ポイント数 3〜12 |
| `m` | ミラー 3枚 / 2枚 |
| `a` `s` | 模様の大きさ 50〜250 |
| `z` `x` | 回転の速さ 0〜100 |
| `i` | 操作一覧をモニターに出す / 消す |
| `0` | 初期設定に戻す |
| `h` | 一覧をシリアルに出す |

同じ一覧を HDMI モニタにも出す。画面の下中央 512x256 px の枠に
32桁 x 8行。PS が AXI の 0x400 以降へ ASCII を書き、PL がフォント ROM
（8x16 を 2 倍に拡大）で描く。枠の中は 1/4 に暗くして文字を読みやすくする。

**はまった点**: 文字の点を枠で区切らないと、枠の外でも桁・行の添字が
折り返して同じ一覧が画面いっぱいに並ぶ。枠の暗さと文字の両方を
同じ「枠の中か」で区切ること。

## 段5c — ピースを PL で描く

### 考え方: 種類を焼き込まず、マイクロコードで持つ

9 種の形は 6 系統しかない（円 / 正多角形 / ゆらぎ円 / カプセル / 箱 / 差集合）。
部品も CORDIC・sin/cos 表・exp 表・log2/exp2 表・逆数・積和 の 6 つで足りる。
そこで **演算器 1 組 + 種類ごとのプログラム** にした。
**種類を足すのは `rtl/pprog.hex` を書き替えるだけで、再合成が要らない。**
`type` は 4bit なので 16 種まで入る（いま 9 種、7 つ空き）。

### 効いた決め事: プログラムは色を扱わない

プログラムが出すのは 3 つだけ。

```
A = 不透明度   K = 粒の色に掛ける係数   W = 白を足す量
最終色 = (粒の色 * K + W) * 奥行きの暗さ
```

9 種すべてがこの形に収まったので、RGB 3 本ぶんの演算がプログラムから消え、
最後に 1 回で済む。

### レーンとは

**算術回路ひと揃い。1 レーンが 1 画素を受け持つ。** 8 レーンが同じ命令を
同時に実行するので、命令メモリも解読回路も 1 組で足りる。
1 レーンは 24 画素を順に回して CORDIC の 21 クロックの遅延を埋める。
8 レーン x 24 画素 = 192 画素が常に処理の途中にある。

### 種類ごとの命令数 (実測)

| 種類 | 命令 | CORDIC | 表 | 種類 | 命令 | CORDIC | 表 |
|---|---|---|---|---|---|---|---|
| 天然石 | 63 | 7 | 3 | ビーズ | 30 | 1 | 3 |

## 段5d-1 — セル画像を BRAM から URAM へ

段5c で **BRAM が 94.1%** になり、これ以上何も積めなくなった。
セル画像 2 枚（奥層 65536 x 16bit + 手前層 65536 x 32bit = 3.1Mb）が
その大半を占めていたので、XCK26 に 18Mb ある URAM へ移した。

結果: **BRAM 135.5 (94.1%) → 41.5 (28.8%)、URAM 0 → 32 (50.0%)**。
LUT・FF・DSP は変わらない。絵も段5c と同じ（置き場所だけを変えたので）。

### ★ URAM の決まり（2025.2 で実際に合成して確かめた。推測ではない）

**1. 初期値を持てない。**
`(* ram_style = "ultra" *)` を付けた配列に `$readmemh` があると

```
WARNING: [Synth 8-12183] ... ignored because a non-zero INIT value
```

が出て、**黙って BRAM に落ちる**（エラーにならないので気づきにくい）。
URAM は電源投入時に必ず全 0 で、初期値を焼く仕組みが無い。

**2. 語まるごとしか書けない。**

```
WARNING: [Synth 8-12186] ... ignored because invalid write mode
```

- 同じ口で「書きながら読む」形は駄目。`if (we) ... else ...` で分ける
- `mem[w][sel*16 +: 16] <= d` のような部分選択は、**添字が定数でも駄目**
- 語全体を書けば載る（実測: 16384 語 x 64bit → URAM 4 個 / BRAM 0）

**3. 深さ 65536 は幅によらず URAM 16 個。**
URAM1 個は 4096 語 x 72bit なので、深さ 65536 は 16 個を縦に繋ぐことになる。
72bit に 4 画素詰めれば 1/4 で済むが、2 のせいで部分書き込みに読み直しが
要るので今はやらない。

**4. クロックが 1 本。** 両方の口が同じクロックで動く。

### 中身をどう入れるか

1 のせいで焼き込めない。起動時に **PS が AXI で流し込む**ことにした。

| 番地 | 名前 | 動き |
|---|---|---|
| `0xA0000180` | `CELL_CTRL` | bit0 で奥層/手前層を選ぶ。書くと番地が 0 に戻る |
| `0xA0000190` | `CELL_DATA` | 今の番地に 1 語入れ、番地が 1 進む |

`vitis_src/main.c` の `LoadCells()` が 65536 語 x 2 枚を書く。**約 13ms**。
AXI クロックから画素クロックへはトグルを 2 段同期で渡している。

流し込むデータは `tools/gen_cell_c.py` が `.hex` から C の配列にする。

```bash
python tools/gen_cell_c.py     # → vitis_src/cell_data.c / .h
```

`cell_data.c` は 1.2MB のソースで、ELF が **+384KB** になる。git には入れず、
上のコマンドで作る（元の `.hex` は git にある）。Vitis 側では
`UserConfig.cmake` の `USER_COMPILE_SOURCES` に `"cell_data.c"` を足すこと。

**段5d-2 で手前層も PL が描くようになれば、この配列は要らなくなる。**

### 口の多重化

セルは 2 口あるが、URAM が初期値を持てないので流し込み用の口が要る。
片方を時期で切り替えた。

| セル | 口A（常時） | 口B |
|---|---|---|
| 奥層 | 折り返しが読む | 起動時=流し込み / 以後=ピース描画の書き込み |
| 手前層 | 折り返しが読む | 起動時=流し込み / 以後=影の読み出し |

### タイミング

**WNS +0.047ns**（段5c は +0.241ns）。違反 0 だが余裕はほぼ無い。
URAM は BRAM より読み出しが遅いので、次に何か足して落ちたら
セル読み出しにレジスタを 1 段入れる（`rtl_top.v` の `TOTAL_LAT` を +1 すれば
`vga_iface` の `PIXEL_DELAY` も追従する）。

## 段5d-2 — 枠にピースを 4 個まで詰める

1 つの枠は `LANES * WARP` = 192 画素ぶんある。ところがラメは 1 個 112 画素
しかないので、1 枠に 1 個しか入れないと **42% が空で回る**。
そこで**同じ種類のピースを 1 つの枠に 4 個まで混ぜる**ことにした。

### 効き具合（`tools/pshade_sched.py` でクロック単位に模擬して実測）

| 枠に混ぜる | 既定 271 個 | 上限 625 個 |
|---|---|---|
| 1 個（段5c） | 0.67 本 / 無駄 **19.3%** | 2.17 本 → **20Hz** / 12.3% |
| 2 個 | 0.54 本 / 4.5% | 1.88 本 → **30Hz** / 2.3% |
| **4 個** | 0.52 本 / **1.6%** | 1.84 本 → **30Hz** / **0.7%** |
| 8 個 | 変わらず | 変わらず |

（ラメの位相のあふれを直して 3 命令増えた後の値。下の「罠 3」を見ること）

**上限構成が 20Hz → 30Hz になる。** 4 個で頭打ちなので 4 個にした。

### ピースの切り替えはスロット境界だけ

1 スロット = `LANES` = 8 画素を 8 レーンが同時に処理する。1 つのスロットに
2 個のピースを混ぜると、ピースごとの定数（seed/e/rot・色・奥行きの暗さ）の
選択が**レーンごと**に要る。それを避けるため、ピースの画素数をスロット単位に
切り上げ、端数（平均 4 画素/ピース）は `lane_valid` を落として捨てる。
上の表はこの端数を含めて測ったもの。

### ピースごとの定数は 4 個ぶんのバンクに持つ

スロットごとに「どのピースか」を 2bit で覚え（`cPS`）、命令を発行する拍に
バンクから選んでレーンへ渡す。合成（色を作るところ）も同じ `cPS` で
色と奥行きの暗さを選ぶ。

バンクに入れるもの: `seed` `e` `rot` `time` ・ 粒の色 RGB ・ 奥行きの暗さ ・
α をすでに掛けた色を出す種類かどうか。**枠の左上の座標**はバンクに入れず、
走査しているピースを取り込んだレジスタ（`cp_x0` `cp_y0`）を使う。

### 渡し方を start/busy から valid/take に変えた

枠を流し終える前に次のピースを受け取る必要があるので、握手を変えた。

```
pdriver → p_valid  入口にピースが乗っている
pdriver ← p_take   並び替え器が取り込んだ (1 クロック)
```

取り込む拍（`S_TAKE`）で枠の大きさ・座標の増分・左上の座標を**自分の
レジスタへ写してから** `p_take` を返す。写さずに入口を直接使うと、
`p_take` のあと入口が次のピースに変わって、書き込み先の番地が狂う。

### 表は種類ごとにまとまっていること

1 つの枠には同じ種類しか入れられない（プログラムが違う）。
`tools/gen_pparts.py` が種類ごとにまとめ、**種類の中は z 順**に並べる。

参照実装 `renderCell()` は z だけでソートして奥から描くので、種類で
まとめると重なりの順序が変わる。その差を `tools/order_test.py` で測った。

| 並べ方 | 参照実装（z 順）との差 | 影響する画素 |
|---|---|---|
| 種類順・**種類の中は z 順** | 平均 **0.285/255** | 1.32% |
| 種類順・種類の中は順不同 | 平均 1.789/255 | 5.64% |

参照実装との差はもともと 9.34/255 あるので、前者なら埋もれる。
**種類の中の z 順は守ること**（順不同にすると 6 倍悪くなる）。

### 検証

`python tools/tb_seq_check.py <種類> 4` で、同じ種類を 4 個、重ならない
位置に並べて流す。**seed・rot・z はすべて違う値にしてある。**
同じ値にすると、枠の中で定数が入れ替わらなくても絵が合ってしまい、
バンクの選択を間違えても気づけない。

9 種すべて **6.90〜8.38 / 255**（RGB565 の青 5bit の量子化と同じ）。

### ★ ここで見つけた罠 2 つ

**1. 関数の中から外の信号を参照すると、継続代入の感度リストに入らない**

```verilog
function signed [W-1:0] pick;      // 中で pcs_r を直に参照していた
  ...
wire signed [W-1:0] va = pick(ra_r, va_r);   // ← 駄目
```

`assign` の感度は**右辺の式に現れる信号だけ**。関数の中で参照している
`pcs_r` が変わっても `va` が作り直されない。段5c までは定数が全スロットで
同じだったので露出しなかった。枠に詰めて初めて、2 個目以降のピースだけ
形が崩れた。**定数は必ず引数で渡すこと。**

見つけ方: `ra_r=4`（= r4 を読む）かつ `pcs_r` は正しい値、なのに
`va` が 1 つ前のピースの値という**矛盾**をダンプで見た。

**2. clamp の前に幅を狭めるとあふれる（`ptrans.v` の SSTEP）**

```verilog
wire signed [2*W-1:0] tprod = num6 * e2r;
wire signed [W-1:0]   traw  = tprod >>> FRAC;   // ← 駄目。ここであふれる
wire signed [W-1:0]   tclp  = (traw < 0) ? 0 : (traw > 1.0) ? 1.0 : traw;
```

smoothstep は結果を 0〜1 に丸めるので、途中の `t` は 1.0 を大きく超えて
よい設計。ところが S6.17 の上限は 64 しかない。棒 (rod) は
`1/(b-a) = 1/(0.8*e)` で、z が 1 に近い（e が小さい）と 38.5 になり、
枠の隅の `d`≈2.3 との積が **89 になってあふれ、符号が反転して clamp が 0 を
返す**。症状は「透明であるべき枠の隅が不透明な色で塗られる」。
z が 0.65 以下だと 56 で収まるので**奥のピースだけ壊れて見える**。
これは段5c から入っていたバグで、実機でも起きていた。

**シフトした後の値も、幅を持った wire に受けてから丸めること。**
CLAUDE.md の「掛け算の式幅」と同じ罠の変種。

**3. ラメの位相が S6.17 をあふれていた（プログラム側）**

```
MULI   ph, rot, 4           ph = rot*4          0〜25.1
MADDC  ph, seed, 60, ph     ph += seed*60       → 最大 85.1  ★あふれる
```

`rot` は 0〜2π、`seed` は 0〜1 なので、合計が **最大 85** になる。
S6.17 の上限は 64 だから符号が反転し、きらめきの位相が狂う。
**既定の構成でラメの 14.6%（220 個中 32 個）が壊れていた。**
段5c から入っていたバグで、実機でも起きていた。

直し方: `seed*60`（最大 60 でぎりぎり入る）を**先に 2π で折り返してから**
`rot*4` を足す。最大 31.4 に収まる。

```
MULI   ph, seed, 60
MULI   pw, ph, 1/(2π)
FLOOR  pw, pw
MADDC  ph, pw, -(2π), ph      ← ここまでで 0〜6.28
MADDC  ph, rot, 4, ph         ← + rot*4 で 0〜31.4
```

3 命令増えてラメは 50 → 53 命令になるが、全体のクロックは **0.74%** しか
増えない。`time` を使うときは PS 側で 2π/0.9 未満に折り返して渡すこと
（`sr = seed*0.6+0.3` が最大 0.9 なので `tt` の上限が 6.28 になる）。

### ★ なぜ見逃していたか — `check()` は 1 点しか試していなかった

`tools/piece_isa.py` の `check()` は **seed=0.37 / rot=0.9 / z=0.7 / t=3.3 の
1 点だけ**でプログラムと正解を突き合わせていた。だから「ある seed と rot の
組み合わせだけであふれる」ものを 9 種すべて「0.00000 で一致」と報告していた。

そこで `check_range()` を足した。**seed 0〜1・rot 0〜2π・z 0〜1 を振って、
命令ごとに結果の絶対値の最大を記録し、±64 を超えるものを挙げる。**

```bash
python tools/piece_isa.py        # 最後に範囲チェックが出る
```

直した後の実測:

| 種類 | いちばん大きい中間値 |
|---|---|
| 色ガラス | RECIP ipl 13.53 |
| 棒 | MULI cy 4.00 |
| 六角柱 | MULI t 4.00 |
| 丸い塊 | MADDC a5 **44.49** |
| 三日月 | MULI g 3.62 |
| ビーズ | LEN d 1.70 |
| 天然石 | MADDC a5 **52.49** |
| ラメ | MULI ph **60.00** |
| 気泡 | MULI sd 20.24 |

全部 ±64 に収まるが、**天然石 52.5・ラメ 60.0 は余裕が少ない**。
プログラムをいじるときは必ずこれを走らせる。

## 段5d-3 — 下の色を読んで α で重ねる

段5c〜5d-2 はピースの色をセルに**上書き**していた。重なり合う所が
後勝ちになり、半透明のピースの下が見えなかった。

### なぜ素直に繋げないか

**URAM は同じ拍で読むか書くかのどちらかしかできない**（段5d-1 の決まり 2）。
ところが合成（`S_BLEND`）は 192 画素を連続して**書く**ので、同じ口で
読みながら書けない。奥層の口 A は折り返しが毎画素引いているので空きが無い。

`S_BLEND` を 2 拍に 1 画素（読み → 書きを交互）にすれば読めるが、
それだと**段5d-2 の改善が吹き飛ぶ**。

| | 上限 625 個 |
|---|---|
| 2 拍に 1 画素 | 1.84 本 → **2.24 本 → 20Hz** |
| **S_EXEC 中に先読み** | **1.84 本のまま 30Hz** |

### 作り: S_EXEC 中に 192 画素を先読みしてレジスタに溜める

`S_EXEC` はプログラムを流す区間で、命令数 × `WARP` 拍ある。
**いちばん短い三日月でも 432 拍**なので、192+2 拍の読みが紛れ込む。

| 種類 | S_EXEC の長さ | 要 194 拍 |
|---|---|---|
| 三日月 | 432 拍 | OK |
| 棒 | 600 拍 | OK |
| 気泡 | 480 拍 | OK |
| 天然石 | 1512 拍 | OK |

`S_EXEC` 中は書き込みが無いので、口 B が空いている。
**クロックは 1 拍も増えない。** 代わりに 192 × 16bit = 3072 FF を使う。

奥層の口 B は 3 通りに使い回す。

| 時期 | 用途 |
|---|---|
| 起動時 | PS からの流し込み（`p_cf_we`） |
| `S_BLEND` 中 | ピース描画の書き込み（`pc_we`） |
| それ以外の拍 | 下の色の先読み（`pc_raddr`） |

### ★ ここで踏んだ罠: 読み出し遅延は 2 拍

`pshade_seq.v` は `cell_raddr = cAD[bi_d1]` と書いてあり、**1 拍遅延を
前提にしていた**。ところが `cell_uram.v` の口 B は `b_q0` → `b_q1` と
2 段持っている（URAM は出力段を持たせた方が速い）。
そのまま繋ぐと下の絵が 1 画素ずれる。

テストベンチ（`sim/tb_seq.v`）も 1 拍だったので、**2 拍に直した**。
でないと実機と合わない。

### 割り切り: 同じ枠の中で重なるピース

先読みなので、**同じ枠に入った 2 つのピースが重なると、後のピースは
先のピースの書き込みを見ない**。段5d-2 の時点でも読みと書きが 1 拍
ずれていて同じ制約があった。実測は下の表のとおり。

| 離す距離 | 枠が重なる画素 | 枠の中の最大の差 |
|---|---|---|
| 0.00（完全に重なる） | 48 | **213.50/255** |
| 0.02 | 30 | 213.50/255 |
| 0.04 | 18 | 7.32/255 |
| 0.08（重ならない） | 0 | 7.49/255 |

実際のピースで起きる頻度（既定 271 個・20 回ぶんの平均）:

| 並べ方 | 重なった組 | 重なった画素 |
|---|---|---|
| 種類順・種類内 z 順 | 2.8% | **全体の 0.240%** |
| 種類順・空間的に散らす | 3.1% | 0.268%（改善せず） |

重なるのは**全体の 0.240% の画素**で、平均への寄与は最悪でも 0.5/255 程度
（参照実装との差 9.34/255 に対して 5%）。bbox が重なっても実体が重なるとは
限らないので実際はさらに小さい。並べ替えでの改善は効果が無かったので
**割り切った**。

別の枠に入れば問題ない（枠ごとに先読みするため）。枠に詰めるのは
同じ種類だけなので、重なるのは同種のピースが隣り合ったときだけ。

### 資源（段5d-2 → 段5d-3）

```
LUT  84133 (71.8%) → 85335 (72.9%)
FF   54010 (23.1%) → 54165 (23.1%)
WNS  +0.614ns      → +0.045ns        ★ 余裕がほとんど無い
合成 48 分         → 56 分
```

`cBG` は FF ではなく **LUTRAM** になった（深さ 192 x 幅 16）。
合成ログにこの警告が出る。

```
RAM Pipeline Warning: Read Address Register Found For RAM cBG_reg.
We will not be able to pipeline it. This may degrade performance.
```

読む番地がレジスタ (`bi_d2`) なので Vivado がパイプライン化できない。
**これが +0.614ns → +0.045ns の主因。** 次に落ちたら `cBG` の出力を
レジスタに受けて 1 段入れる（`bi_d3` を足して合成を 1 拍ずらす）。

### ★ 効き目は目では分からない（`tools/blend_effect.py` で実測）

実機で見比べても違いが分からなかったので、**どれだけ変わるはずなのか**を
測った。

| 上書き（段5d-2 まで） vs α 合成（段5d-3） | |
|---|---|
| 平均の差 | **1.219 / 255** |
| 最大の差 | 22.0 / 255 |
| 8/255 を超える画素 | 8.83% |

**油の地が暗い**（RGB 14,11,20 / 255）ので、上書きしても α 合成しても
色があまり変わらない。しかも万華鏡の折り返しで縮小される。
**実機で分からないのが正常。**

`sim/blend_effect.png` の差の画像を見ると、**ピースの bbox の四角が
浮き出ている**。上書きだと「ほぼ透明な画素」でも地を潰していたぶん。
平均 1.219/255 は参照実装との差 9.34/255 の 13% にあたるので、
数字としては意味のある改善。

### 検証

`python tools/tb_seq_check.py <種類> 4 0.015 oil` で、**油の地を下敷きに**
4 個詰めて流す。黒地だと α の効きが見えないので、重ねる実装を
確かめるには `oil` が要る。

下地は RTL と同じ RGB565 の量子化を通した値を使う。float のままだと
丸めのぶんだけ差が出て、重ねる実装の良否が見えない。

9 種とも **7.18〜9.57 / 255**（RGB565 の青 5bit の量子化と同じ範囲）。

| 種類 | 枠の中の平均 | 最大 |
|---|---|---|
| 色ガラス | 1.25 | 7.45 |
| 棒 | 0.62 | 7.32 |
| 六角柱 | 0.89 | 8.29 |
| 丸い塊 | 1.28 | 7.39 |
| 三日月 | 0.85 | 8.10 |
| ビーズ | 1.46 | 7.18 |
| 天然石 | 1.08 | 8.08 |
| ラメ | 2.27 | 9.37 |

ラメと気泡は premul（α を織り込んだ色を出す種類）なので少し大きい。
