# 万華鏡を KV260 の FPGA で動かす

ブラウザで動いている「オイル万華鏡」と同じ映像を、Kria KV260 の PL で毎画素計算して
HDMI に出す。

参照実装（目標の映像そのもの）:

```
E:\Dropbox\claude\APP\kaleidoscope\index.html
```

WebGL2 / 単一 HTML / 1592 行。ブラウザで開くだけで動く。

## 何をしているか

万華鏡は「のぞき穴から出た光線を、三角形に並べた3枚の鏡で反射させながら奥へ進め、
セル面（オイルとピースが入った部屋）に届いた位置の色を見る」もの。

鏡は筒の軸と平行なので、光線追跡は**断面の 2D 問題**に落ちる。
これを 1 画素 1 クロックの 16 段パイプラインにして PL に載せた。

```
画素座標 ──> slope = sp/focal ──> p = slope*Z_MIRROR ──┐
                                                        │
      ┌─────────────────────────────────────────────────┘
      v
  [ scope_stage x16 ]   1段 = 3枚の壁との交差判定 + 反射
      │
      v
  c = p / TUBE_R ──> cell_mem (セル画像) ──> 減光 ──> 周辺減光 ──> HDMI
```

### パイプラインを軽くした2つの工夫

**1. 光線を正規化しない**

`p(z) = slope * z` なので、媒介変数に奥行き z をそのまま使える。
参照実装の

```glsl
float sl = length(slope);
vec2 dir = slope / sl;
float remain = sl * (Z_CELL - Z_MIRROR);
```

は、`dir = slope`（正規化しない）、`remain = Z_CELL - Z_MIRROR`（**全画素で同じ定数**）
と完全に等価。平方根も正規化の除算も要らなくなる。

**2. 一番近い壁を選ぶのに除算を使わない**

```
t_w = a_w / dn_w        a_w = wd_w - dot(p, n_w),  dn_w = dot(dir, n_w) > 0
t_i < t_j  ⟺  a_i * dn_j < a_j * dn_i
```

掛け算の大小比較で最小の壁を決め、**選ばれた1枚だけ除算**する。
残り距離との比較（`t < remain ⟺ a < remain * dn`）も同じ手で除算不要。
結果、1段あたり除算は1個。

除算器も IP を使わず、逆数表（512エントリ）+ ニュートン1回で組んだ（`divq.v`）。

## 数の形式（固定小数点）

| 量 | 形式 | 幅 | 範囲 / 分解能 |
|---|---|---|---|
| p, dir | Q3.15 | 18bit 符号付き | ±4 / 3.1e-5 cm |
| 法線 n | Q2.16 | 18bit 符号付き | \|n\| = 1 |
| a, wd | Q4.14 | 18bit 符号付き | ±8 |
| dn | Q3.15 | 18bit 符号付き | |
| q, remain | Q6.14 | 20bit 符号なし | 0〜11.9 |

18bit に揃えてあるので、掛け算はすべて DSP48E2 1個に収まる。

浮動小数点の正解（`tools/ref_scope.py`）と比べて **平均誤差 0.32/255、反射回数の不一致 0.14%**。

## 筒の寸法

```
TUBE_R   = 2.25 cm   筒の内側の半径 = セルの半径
Z_MIRROR = 0.3  cm   のぞき穴 → 鏡の手前の端
Z_CELL   = 12.2 cm   のぞき穴 → セル手前層
鏡の外接円 R = 2.05 cm、頂角 180/ポイント数
```

反射回数はポイント数8・傾き0で最大16回（実測、`tools/refl_hist.py`）。
だから K=16 で足りる。平均は 7.5 回。

## 作り方

### 1. シミュレーションで絵を確かめる

```bash
python tools/gen_hex.py           # 表とテストセル画像を作る
cp rtl/cell_real.hex rtl/cell_init.hex   # 本物のセル画像を使う場合
bash sim/run_sim.sh               # xsim で 1 フレーム回す (約6分)
python tools/cmp_rtl.py           # モデルと突き合わせて PNG を出す
```

`sim/rtl_scope.png` が RTL の出力、`sim/model_cell256.png` がモデルの出力。
差が大きい画素は `sim/diff.png` に赤で出る。

### 2. 合成

```
E:\vivado\2025.2\Vivado\bin\vivado.bat -mode batch -source E:/fpga/kria260/kaleidoscope/vivado.tcl
```

`project_1/design_1_wrapper.xsa` ができる。

### 3. 実機（ベアメタル Vitis）

SD カードは抜いておく。ただしこの KV260 は **QSPI にブートイメージがあるので
SD を抜いてもフルブートする**。それを前提にした手順が下の 8〜11。

1. Vitis Unified IDE を起動、ワークスペース `E:\Xilinx\project_vitis\ws_kv260_kaleido` を新規作成
2. Platform Component を作成し、`project_1/design_1_wrapper.xsa` を指定
3. Application Component `kaleido_app` を作成、Platform に紐付け
4. `vitis_src/main.c` をワークスペースの `src/` に **ファイルコピーで**同期（IDE の Import だけでは元ファイルの変更が反映されない）
5. `UserConfig.cmake` に `"../main.c"` の行が混入していたら削除。`USER_LINK_LIBRARIES` に `m` を追加（DP ドライバが `nearbyint` を使う）
6. Platform → Build、Application → Build
7. KV260 の電源を入れ、USB-UART のシリアル端末（115200）を開く
8. シリアルに `ZynqMP>` の U-Boot プロンプトが出たら、そのまま待つ
   （この個体は QSPI ブートなので SD を抜いてもここまで進む）
9. Debug Configuration は **Board Initialization = FSBL** のままでよい
   （映像系の成功例 pong / chip8 / rect / tetris はすべて FSBL）。
   駄目なら TCL に切り替える
10. Debug 実行 → `main` で停止 → **Resume**
11. HDMI モニタに映像、UART に `KV260 Kaleidoscope Start` が出る

`Failed to detect FSBL exit status using symbol: XFsbl_Exit` は警告。
シリアルに出力が出ていればアプリは動いている。

ワークスペースを再利用すると `_ide/bitstream/` が自動更新されない。
`.bit` を手で置き換えるか、ワークスペースを作り直すこと。

### 4. 実機の起動 (xsdb。Vitis の画面を使わない。2026-10-18)

Vitis の Debug は **電源投入直後に FSBL で止まることが多い**
(`Failed to detect FSBL exit status using symbol: XFsbl_Exit`)。
FSBL を使わず、**USB の初期化を外した psu_init.tcl** で PS を初期化すると止まらない
(電源投入直後 1 回 + 続けて 2 回、すべて成功)。

```
# 1. USB を外した psu_init を作る (XSA を変えたら作り直す)
python tools/make_psu_nousb.py <WS>/kaleido_plat/export/kaleido_plat/hw/psu_init.tcl <出力>/psu_nousb.tcl
# 2. アプリをビルド (アプリの build/ で。PATH に cmake と aarch64 gcc を足す)
E:/vivado/2025.2/Vitis/bin/ninja.exe
# 3. 起動 (Tera Term は閉じておく)
python tools/serlog.py COM14 <秒> <ログ>          # 裏で回してシリアルを記録
E:/vivado/2025.2/Vitis/bin/xsdb.bat tools/xsdb_run.tcl <WS> <出力>/psu_nousb.tcl
python tools/sendkey.py <キー> <回数> <間隔秒>      # キー操作もシリアルから送れる
```

`xsdb_run.tcl` の流れ: 起動モードを JTAG にしてリセット (Vitis の `set_bootmode` と同じ)
→ PL を書く → `psu_init` (USB 抜き) → PS-PL 分離解除・PL リセット解除 → アプリ。

**止まっていた原因**: この個体は QSPI から起動し、電源投入時に QSPI の U-Boot が
USB の初期化に失敗する (`No working controllers found`)。そのあと USB PHY から
クロックが出ないことがあり、psu_init が USB コントローラのレジスタ
(`0xFE20C200` GUSB2PHYCFG ほか 4 つ) に書いたところでバスが固まる。
止まった FSBL の PC を `aarch64-none-elf-addr2line -f -e fsbl.elf` で引いて分かった。

#### ★★ USB (マウス・キーボード) を使うとき
**この方式は使えない。** USB の初期化を外しているので、USB は動かない。
USB を使うなら、先に「電源投入直後に USB PHY のクロックが無い」問題を解くこと。
- PHY のリセットは psu_init が起動モード端子で行っている (`BOOT_PIN_CTRL` 0xFF5E0250、
  Low を 5μs → High)。リセットの長さか、その後の待ちが足りない疑い (未確認)
- Vivado で USB を無効にする手は失敗した。USB を切る、またはリセット方式を Disable に
  すると、Vivado が USB リセット端子 = MIO 4 を自動で設定し、QSPI (x4) と衝突してエラーになる

## 操作

KV260 にはキーボードもマウスも標準では無い。既につながっている USB-UART を
入力に使う。Tera Term（115200）でキーを打つと設定が変わる。
**JIS 配列で Shift が要るキー（`<` `>` `+` `=`）は使わない。**

| キー | 動き |
|---|---|
| `q` `w` | ポイント数 3〜12（11 以上は K=16 では外側が崩れる） |
| `m` | ミラー 3枚 / 2枚 |
| `a` `s` | 模様の大きさ 50〜250 |
| `z` `x` | 回転の速さ 0〜100 |
| `r` | 往復モード: 一定時間ごとに回転の向きを反転。切 → 5秒 → 10秒 → 20秒 → 切 |
| `v` `b` | 油の粘り 0〜100（小さいほどサラサラ） |
| `e` | かき混ぜる |
| `j` `l` | 筒を手で左 / 右に回す |
| `c` | 色の組み合わせ 6 通り |
| `p` | 配色エディタ（下の表） |
| `i` | 操作一覧をモニターに出す / 消す |
| `0` | 初期設定に戻す |
| `h` | 一覧をシリアルに出し、モニターの文字をキーの並びの絵と切り替える |

シリアルの一覧はキーボードの並びで出す（日本語は 1 文字 2 桁として 80 桁に収める）。
`h` を押すとモニターの文字も「1 行目にキー、2 行目に働きの略語 2 文字」を 4 段並べた絵になる
（32桁 x 8行に入れるため。略語の意味はシリアルの一覧の下に出る）。

300 フレームごとの描き直し回数・物理演算の時間は、キー一覧が流れて読めなくなるので
普段は出さない。測るときは `main.c` の `SHOW_STATS` を 1 にする。

### 配色エディタ（`p` で開く・`p` で閉じる）

エディタの中ではキーの意味が変わる。**キーを送る前に、エディタが開いているかを確かめること。**

| キー | 動き |
|---|---|
| `q` `w` | 種類 BEAD S.BEAD GLASS GLITTER STONE HEX ROD BLOB MOON SPARK（選んだ種類のピースが点滅） |
| `a` `s` | 色の番号 1〜8 |
| `e` `d` / `r` `f` / `t` `g` | 赤 / 緑 / 青 の + / −（8 ずつ） |
| `y` `h` | 割合 + / −（5% ずつ。0 の色は使わない） |
| `u` `j` / `i` `k` / `o` `l` | SPARK のときだけ。きらめき層の量 / 明るさ / 大きさ |
| `c` | 組み込みの組を写す（今の直しは消える） |
| `1`〜`4` | SD の `KPAL1.TXT`〜`KPAL4.TXT` に保存 |
| `5`〜`8` | `KPAL1.TXT`〜`KPAL4.TXT` を読み込む |
| `/` `?` | キー一覧（モニターもキーの並びの絵と切り替える） |

起動時に `KPAL1.TXT` があれば読む。中身は文字なので PC で直してもよい。

```
# KV260 kaleidoscope colors (SLOT1)
BEAD FFFFFF/25 FFD778/25 FF96AA/25 96DCFF/25 000000/0 000000/0 000000/0 000000/0
...                        (種類ごとに「RRGGBB/割合」が 8 つ。書いていない種類は今の色のまま)
SPKPARAM 45 100 75         きらめき層の量 [%]・明るさ [%]・大きさ [画素 x100]
SETTING 6 3 130 50 10 30   ポイント・ミラー・大きさ・回転・往復 [秒]・粘り (無ければ設定は変えない)
```

SD には 4 つ入れてある（2026-10-23）: 1 = SLOT1 の色・初期設定 / 2 = 6,3,130,50,10,30 /
3 = JEWEL・10,3,80,20,切,80（細かくゆっくり）/ 4 = RAINBOW・4,2,180,80,5,10（大きく速く）。

BSP に xilffs（FatFs）が要る。Vitis の `kaleido_app/src/UserConfig.cmake` の
`USER_LINK_LIBRARIES` に xilffs を足す（リポジトリの外）。

同じ一覧を HDMI モニタにも出す。画面の下中央 512x256 px の枠に
32桁 x 8行。PS が AXI の 0x400 以降へ ASCII を書き、PL がフォント ROM
（8x16 を 2 倍に拡大）で描く。枠の中は 1/4 に暗くして文字を読みやすくする。

**はまった点**: 文字の点を枠で区切らないと、枠の外でも桁・行の添字が
折り返して同じ一覧が画面いっぱいに並ぶ。枠の暗さと文字の両方を
同じ「枠の中か」で区切ること。

## 段5c — ピースを PL で描く

### 考え方: 種類を焼き込まず、マイクロコードで持つ

9 種の形は 6 系統しかない（円 / 正多角形 / ゆらぎ円 / カプセル / 箱 / 差集合）。
部品も CORDIC・sin/cos 表・exp 表・log2/exp2 表・逆数・積和 の 6 つで足りる。
そこで **演算器 1 組 + 種類ごとのプログラム** にした。
**種類を足すのは `rtl/pprog.hex` を書き替えるだけで、再合成が要らない。**
`type` は 4bit なので 16 種まで入る（いま 9 種、7 つ空き）。

### 効いた決め事: プログラムは色を扱わない

プログラムが出すのは 3 つだけ。

```
A = 不透明度   K = 粒の色に掛ける係数   W = 白を足す量
最終色 = (粒の色 * K + W) * 奥行きの暗さ
```

9 種すべてがこの形に収まったので、RGB 3 本ぶんの演算がプログラムから消え、
最後に 1 回で済む。

### レーンとは

**算術回路ひと揃い。1 レーンが 1 画素を受け持つ。** 8 レーンが同じ命令を
同時に実行するので、命令メモリも解読回路も 1 組で足りる。
1 レーンは 24 画素を順に回して CORDIC の 21 クロックの遅延を埋める。
8 レーン x 24 画素 = 192 画素が常に処理の途中にある。

### 種類ごとの命令数 (実測)

| 種類 | 命令 | CORDIC | 表 | 種類 | 命令 | CORDIC | 表 |
|---|---|---|---|---|---|---|---|
| 天然石 | 63 | 7 | 3 | ビーズ | 30 | 1 | 3 |
| ラメ | 50 | 4 | 6 | 棒 | 25 | 1 | 2 |
| 色ガラス | 40 | 2 | 2 | 気泡 | 20 | 2 | 3 |
| 六角柱 | 38 | 1 | 4 | 三日月 | 18 | 2 | 1 |
| 丸い塊 | 31 | 4 | 2 | | | | |

毎画素の初期値は種類ごとに 2〜4 個（`qx qy vqx vqy` のうち使うものだけ）。
`seed` `e` `rot` `time` はピースごとに一定なのでレーンの定数バンクに置く。
`z` はどのプログラムも読まない。

### 速さ (クロック単位の模擬。`tools/pshade_sched.py`)

| レーン | 既定 271 個 | 上限 625 個 |
|---|---|---|
| 8 | 0.51 本 → **60Hz** | 1.81 本 → **30Hz** |
| 12 | 0.35 本 → 60Hz | 1.21 本 → 30Hz |
| 16 | 0.26 本 → 60Hz | 0.92 本 → 60Hz |

12 レーンにしても上限は 30Hz のままで無駄。**8 レーンに決めた。**

**枠にピースを詰めるかどうかが効く。** ラメは 1 個 112 画素しかなく、
枠は 192 画素あるので、詰めないと 3 割捨てる（無駄 8〜12% → 0.2%）。
4 個混ぜられれば十分で、それ以上は効かない。

### 検証

すべて Python の正解と突き合わせてある。

| 何を | 結果 |
|---|---|
| 参照実装の移植 (`ref_cell.py`) | 本物と **0.21/255** |
| 9 種のプログラム (`piece_isa.py`) | 正解と **0.00000** |
| アセンブラ (`pasm.py`) | 丸めなしで **0.00000** |
| 演算器 1 レーン (`tb_lane_check.py`) | 7 種 **0.01〜0.07/255**、ビーズ 1.64、天然石 2.18 |
| 座標生成 (`tb_pixgen_check.py`) | 4 通りの枠で一致 |
| 並び替え器 (`tb_seq_check.py`) | 9 種 **6.90〜8.38/255** (4 個詰めて) |

★ ここの数字は 2026-10-09 に測り直したもの。**以前は「9 種 0.02〜0.07」と
書いてあったが実測と違っていた。** ビーズは K が 1.07e-2、天然石は A/K/W が
3〜8e-3 ずれる (表引きの精度。RGB565 の 1 階調 = 8.2/255 よりは小さい)。

レーン単体は A/K/W の差を色に換算したもの (量子化なし)。並び替え器は
セルに書いた RGB565 と比べるので、**量子化が支配的**で 8〜9.3/255 になる。
これは RGB565 の青 5bit (8.2 階調) とほぼ一致する。

## 段5d-1 — セル画像を BRAM から URAM へ

段5c で **BRAM が 94.1%** になり、これ以上何も積めなくなった。
セル画像 2 枚（奥層 65536 x 16bit + 手前層 65536 x 32bit = 3.1Mb）が
その大半を占めていたので、XCK26 に 18Mb ある URAM へ移した。

結果: **BRAM 135.5 (94.1%) → 41.5 (28.8%)、URAM 0 → 32 (50.0%)**。
LUT・FF・DSP は変わらない。絵も段5c と同じ（置き場所だけを変えたので）。

### ★ URAM の決まり（2025.2 で実際に合成して確かめた。推測ではない）

**1. 初期値を持てない。**
`(* ram_style = "ultra" *)` を付けた配列に `$readmemh` があると

```
WARNING: [Synth 8-12183] ... ignored because a non-zero INIT value
```

が出て、**黙って BRAM に落ちる**（エラーにならないので気づきにくい）。
URAM は電源投入時に必ず全 0 で、初期値を焼く仕組みが無い。

**2. 語まるごとしか書けない。**

```
WARNING: [Synth 8-12186] ... ignored because invalid write mode
```

- 同じ口で「書きながら読む」形は駄目。`if (we) ... else ...` で分ける
- `mem[w][sel*16 +: 16] <= d` のような部分選択は、**添字が定数でも駄目**
- 語全体を書けば載る（実測: 16384 語 x 64bit → URAM 4 個 / BRAM 0）

**3. 深さ 65536 は幅によらず URAM 16 個。**
URAM1 個は 4096 語 x 72bit なので、深さ 65536 は 16 個を縦に繋ぐことになる。
72bit に 4 画素詰めれば 1/4 で済むが、2 のせいで部分書き込みに読み直しが
要るので今はやらない。

**4. クロックが 1 本。** 両方の口が同じクロックで動く。

### 中身をどう入れるか

1 のせいで焼き込めない。起動時に **PS が AXI で流し込む**ことにした。

| 番地 | 名前 | 動き |
|---|---|---|
| `0xA0000180` | `CELL_CTRL` | bit0 で奥層/手前層を選ぶ。書くと番地が 0 に戻る |
| `0xA0000190` | `CELL_DATA` | 今の番地に 1 語入れ、番地が 1 進む |

`vitis_src/main.c` の `LoadCells()` が 65536 語 x 2 枚を書く。**約 13ms**。
AXI クロックから画素クロックへはトグルを 2 段同期で渡している。

流し込むデータは `tools/gen_cell_c.py` が `.hex` から C の配列にする。

```bash
python tools/gen_cell_c.py     # → vitis_src/cell_data.c / .h
```

`cell_data.c` は 1.2MB のソースで、ELF が **+384KB** になる。git には入れず、
上のコマンドで作る（元の `.hex` は git にある）。Vitis 側では
`UserConfig.cmake` の `USER_COMPILE_SOURCES` に `"cell_data.c"` を足すこと。

**段5d-2 で手前層も PL が描くようになれば、この配列は要らなくなる。**

### 口の多重化

セルは 2 口あるが、URAM が初期値を持てないので流し込み用の口が要る。
片方を時期で切り替えた。

| セル | 口A（常時） | 口B |
|---|---|---|
| 奥層 | 折り返しが読む | 起動時=流し込み / 以後=ピース描画の書き込み |
| 手前層 | 折り返しが読む | 起動時=流し込み / 以後=影の読み出し |

### タイミング

**WNS +0.047ns**（段5c は +0.241ns）。違反 0 だが余裕はほぼ無い。
URAM は BRAM より読み出しが遅いので、次に何か足して落ちたら
セル読み出しにレジスタを 1 段入れる（`rtl_top.v` の `TOTAL_LAT` を +1 すれば
`vga_iface` の `PIXEL_DELAY` も追従する）。

## 段5d-2 — 枠にピースを 4 個まで詰める

1 つの枠は `LANES * WARP` = 192 画素ぶんある。ところがラメは 1 個 112 画素
しかないので、1 枠に 1 個しか入れないと **42% が空で回る**。
そこで**同じ種類のピースを 1 つの枠に 4 個まで混ぜる**ことにした。

### 効き具合（`tools/pshade_sched.py` でクロック単位に模擬して実測）

| 枠に混ぜる | 既定 271 個 | 上限 625 個 |
|---|---|---|
| 1 個（段5c） | 0.67 本 / 無駄 **19.3%** | 2.17 本 → **20Hz** / 12.3% |
| 2 個 | 0.54 本 / 4.5% | 1.88 本 → **30Hz** / 2.3% |
| **4 個** | 0.52 本 / **1.6%** | 1.84 本 → **30Hz** / **0.7%** |
| 8 個 | 変わらず | 変わらず |

（ラメの位相のあふれを直して 3 命令増えた後の値。下の「罠 3」を見ること）

**上限構成が 20Hz → 30Hz になる。** 4 個で頭打ちなので 4 個にした。

### ピースの切り替えはスロット境界だけ

1 スロット = `LANES` = 8 画素を 8 レーンが同時に処理する。1 つのスロットに
2 個のピースを混ぜると、ピースごとの定数（seed/e/rot・色・奥行きの暗さ）の
選択が**レーンごと**に要る。それを避けるため、ピースの画素数をスロット単位に
切り上げ、端数（平均 4 画素/ピース）は `lane_valid` を落として捨てる。
上の表はこの端数を含めて測ったもの。

### ピースごとの定数は 4 個ぶんのバンクに持つ

スロットごとに「どのピースか」を 2bit で覚え（`cPS`）、命令を発行する拍に
バンクから選んでレーンへ渡す。合成（色を作るところ）も同じ `cPS` で
色と奥行きの暗さを選ぶ。

バンクに入れるもの: `seed` `e` `rot` `time` ・ 粒の色 RGB ・ 奥行きの暗さ ・
α をすでに掛けた色を出す種類かどうか。**枠の左上の座標**はバンクに入れず、
走査しているピースを取り込んだレジスタ（`cp_x0` `cp_y0`）を使う。

### 渡し方を start/busy から valid/take に変えた

枠を流し終える前に次のピースを受け取る必要があるので、握手を変えた。

```
pdriver → p_valid  入口にピースが乗っている
pdriver ← p_take   並び替え器が取り込んだ (1 クロック)
```

取り込む拍（`S_TAKE`）で枠の大きさ・座標の増分・左上の座標を**自分の
レジスタへ写してから** `p_take` を返す。写さずに入口を直接使うと、
`p_take` のあと入口が次のピースに変わって、書き込み先の番地が狂う。

### 表は種類ごとにまとまっていること

1 つの枠には同じ種類しか入れられない（プログラムが違う）。
`tools/gen_pparts.py` が種類ごとにまとめ、**種類の中は z 順**に並べる。

参照実装 `renderCell()` は z だけでソートして奥から描くので、種類で
まとめると重なりの順序が変わる。その差を `tools/order_test.py` で測った。

| 並べ方 | 参照実装（z 順）との差 | 影響する画素 |
|---|---|---|
| 種類順・**種類の中は z 順** | 平均 **0.285/255** | 1.32% |
| 種類順・種類の中は順不同 | 平均 1.789/255 | 5.64% |

参照実装との差はもともと 9.34/255 あるので、前者なら埋もれる。
**種類の中の z 順は守ること**（順不同にすると 6 倍悪くなる）。

### 検証

`python tools/tb_seq_check.py <種類> 4` で、同じ種類を 4 個、重ならない
位置に並べて流す。**seed・rot・z はすべて違う値にしてある。**
同じ値にすると、枠の中で定数が入れ替わらなくても絵が合ってしまい、
バンクの選択を間違えても気づけない。

9 種すべて **6.90〜8.38 / 255**（RGB565 の青 5bit の量子化と同じ）。

### ★ ここで見つけた罠 2 つ

**1. 関数の中から外の信号を参照すると、継続代入の感度リストに入らない**

```verilog
function signed [W-1:0] pick;      // 中で pcs_r を直に参照していた
  ...
wire signed [W-1:0] va = pick(ra_r, va_r);   // ← 駄目
```

`assign` の感度は**右辺の式に現れる信号だけ**。関数の中で参照している
`pcs_r` が変わっても `va` が作り直されない。段5c までは定数が全スロットで
同じだったので露出しなかった。枠に詰めて初めて、2 個目以降のピースだけ
形が崩れた。**定数は必ず引数で渡すこと。**

見つけ方: `ra_r=4`（= r4 を読む）かつ `pcs_r` は正しい値、なのに
`va` が 1 つ前のピースの値という**矛盾**をダンプで見た。

**2. clamp の前に幅を狭めるとあふれる（`ptrans.v` の SSTEP）**

```verilog
wire signed [2*W-1:0] tprod = num6 * e2r;
wire signed [W-1:0]   traw  = tprod >>> FRAC;   // ← 駄目。ここであふれる
wire signed [W-1:0]   tclp  = (traw < 0) ? 0 : (traw > 1.0) ? 1.0 : traw;
```

smoothstep は結果を 0〜1 に丸めるので、途中の `t` は 1.0 を大きく超えて
よい設計。ところが S6.17 の上限は 64 しかない。棒 (rod) は
`1/(b-a) = 1/(0.8*e)` で、z が 1 に近い（e が小さい）と 38.5 になり、
枠の隅の `d`≈2.3 との積が **89 になってあふれ、符号が反転して clamp が 0 を
返す**。症状は「透明であるべき枠の隅が不透明な色で塗られる」。
z が 0.65 以下だと 56 で収まるので**奥のピースだけ壊れて見える**。
これは段5c から入っていたバグで、実機でも起きていた。

**シフトした後の値も、幅を持った wire に受けてから丸めること。**
CLAUDE.md の「掛け算の式幅」と同じ罠の変種。

**3. ラメの位相が S6.17 をあふれていた（プログラム側）**

```
MULI   ph, rot, 4           ph = rot*4          0〜25.1
MADDC  ph, seed, 60, ph     ph += seed*60       → 最大 85.1  ★あふれる
```

`rot` は 0〜2π、`seed` は 0〜1 なので、合計が **最大 85** になる。
S6.17 の上限は 64 だから符号が反転し、きらめきの位相が狂う。
**既定の構成でラメの 14.6%（220 個中 32 個）が壊れていた。**
段5c から入っていたバグで、実機でも起きていた。

直し方: `seed*60`（最大 60 でぎりぎり入る）を**先に 2π で折り返してから**
`rot*4` を足す。最大 31.4 に収まる。

```
MULI   ph, seed, 60
MULI   pw, ph, 1/(2π)
FLOOR  pw, pw
MADDC  ph, pw, -(2π), ph      ← ここまでで 0〜6.28
MADDC  ph, rot, 4, ph         ← + rot*4 で 0〜31.4
```

3 命令増えてラメは 50 → 53 命令になるが、全体のクロックは **0.74%** しか
増えない。`time` を使うときは PS 側で 2π/0.9 未満に折り返して渡すこと
（`sr = seed*0.6+0.3` が最大 0.9 なので `tt` の上限が 6.28 になる）。

### ★ なぜ見逃していたか — `check()` は 1 点しか試していなかった

`tools/piece_isa.py` の `check()` は **seed=0.37 / rot=0.9 / z=0.7 / t=3.3 の
1 点だけ**でプログラムと正解を突き合わせていた。だから「ある seed と rot の
組み合わせだけであふれる」ものを 9 種すべて「0.00000 で一致」と報告していた。

そこで `check_range()` を足した。**seed 0〜1・rot 0〜2π・z 0〜1 を振って、
命令ごとに結果の絶対値の最大を記録し、±64 を超えるものを挙げる。**

```bash
python tools/piece_isa.py        # 最後に範囲チェックが出る
```

直した後の実測:

| 種類 | いちばん大きい中間値 |
|---|---|
| 色ガラス | RECIP ipl 13.53 |
| 棒 | MULI cy 4.00 |
| 六角柱 | MULI t 4.00 |
| 丸い塊 | MADDC a5 **44.49** |
| 三日月 | MULI g 3.62 |
| ビーズ | LEN d 1.70 |
| 天然石 | MADDC a5 **52.49** |
| ラメ | MULI ph **60.00** |
| 気泡 | MULI sd 20.24 |

全部 ±64 に収まるが、**天然石 52.5・ラメ 60.0 は余裕が少ない**。
プログラムをいじるときは必ずこれを走らせる。

## 段5d-3 — 下の色を読んで α で重ねる

段5c〜5d-2 はピースの色をセルに**上書き**していた。重なり合う所が
後勝ちになり、半透明のピースの下が見えなかった。

### なぜ素直に繋げないか

**URAM は同じ拍で読むか書くかのどちらかしかできない**（段5d-1 の決まり 2）。
ところが合成（`S_BLEND`）は 192 画素を連続して**書く**ので、同じ口で
読みながら書けない。奥層の口 A は折り返しが毎画素引いているので空きが無い。

`S_BLEND` を 2 拍に 1 画素（読み → 書きを交互）にすれば読めるが、
それだと**段5d-2 の改善が吹き飛ぶ**。

| | 上限 625 個 |
|---|---|
| 2 拍に 1 画素 | 1.84 本 → **2.24 本 → 20Hz** |
| **S_EXEC 中に先読み** | **1.84 本のまま 30Hz** |

### 作り: S_EXEC 中に 192 画素を先読みしてレジスタに溜める

`S_EXEC` はプログラムを流す区間で、命令数 × `WARP` 拍ある。
**いちばん短い三日月でも 432 拍**なので、192+2 拍の読みが紛れ込む。

| 種類 | S_EXEC の長さ | 要 194 拍 |
|---|---|---|
| 三日月 | 432 拍 | OK |
| 棒 | 600 拍 | OK |
| 気泡 | 480 拍 | OK |
| 天然石 | 1512 拍 | OK |

`S_EXEC` 中は書き込みが無いので、口 B が空いている。
**クロックは 1 拍も増えない。** 代わりに 192 × 16bit = 3072 FF を使う。

奥層の口 B は 3 通りに使い回す。

| 時期 | 用途 |
|---|---|
| 起動時 | PS からの流し込み（`p_cf_we`） |
| `S_BLEND` 中 | ピース描画の書き込み（`pc_we`） |
| それ以外の拍 | 下の色の先読み（`pc_raddr`） |

### ★ ここで踏んだ罠: 読み出し遅延は 2 拍

`pshade_seq.v` は `cell_raddr = cAD[bi_d1]` と書いてあり、**1 拍遅延を
前提にしていた**。ところが `cell_uram.v` の口 B は `b_q0` → `b_q1` と
2 段持っている（URAM は出力段を持たせた方が速い）。
そのまま繋ぐと下の絵が 1 画素ずれる。

テストベンチ（`sim/tb_seq.v`）も 1 拍だったので、**2 拍に直した**。
でないと実機と合わない。

### 割り切り: 同じ枠の中で重なるピース

先読みなので、**同じ枠に入った 2 つのピースが重なると、後のピースは
先のピースの書き込みを見ない**。段5d-2 の時点でも読みと書きが 1 拍
ずれていて同じ制約があった。実測は下の表のとおり。

| 離す距離 | 枠が重なる画素 | 枠の中の最大の差 |
|---|---|---|
| 0.00（完全に重なる） | 48 | **213.50/255** |
| 0.02 | 30 | 213.50/255 |
| 0.04 | 18 | 7.32/255 |
| 0.08（重ならない） | 0 | 7.49/255 |

実際のピースで起きる頻度（既定 271 個・20 回ぶんの平均）:

| 並べ方 | 重なった組 | 重なった画素 |
|---|---|---|
| 種類順・種類内 z 順 | 2.8% | **全体の 0.240%** |
| 種類順・空間的に散らす | 3.1% | 0.268%（改善せず） |

重なるのは**全体の 0.240% の画素**で、平均への寄与は最悪でも 0.5/255 程度
（参照実装との差 9.34/255 に対して 5%）。bbox が重なっても実体が重なるとは
限らないので実際はさらに小さい。並べ替えでの改善は効果が無かったので
**割り切った**。

別の枠に入れば問題ない（枠ごとに先読みするため）。枠に詰めるのは
同じ種類だけなので、重なるのは同種のピースが隣り合ったときだけ。

だったので、先に直した。

合成ログの

を見て「`cBG` に 1 段入れれば済む」と考えたが、**最悪パスを実測したら

## 段5d-5 / 5d-6 — 手前層も PL で描く

段5d-4 まで、手前層（z >= 0.5 のピース）は参照実装から取り出した絵を
PS が起動時に流し込んでいた。これを PL が描くようにした。

```
cell_data.c  1206KB → 470KB     手前層の配列が要らなくなった
ELF          +384KB → +128KB
流し込み      13ms  → 8.6ms     (手前層は 0 で埋めるだけ)
表            64 個 → 271 個    奥層 133 / 手前層 138
```

### 手前層は α も重ねる

手前層は `{ablur, a, rgb565}` の 32bit。奥層（不透明な RGB565）と違い、
**ピース同士が重なるとき α も合成する**。

```
色 : rgb_out = rgb_src + rgb_dst * (1 - a_src)    奥層と同じ
α  : a_out   = a_src   + a_dst   * (1 - a_src)    手前層だけ
```

`ablur`（影用のぼかした α）は `a` をそのままコピーしている。参照実装は
α を 2x2 で平均したものを使うが、**ぼかさなくても差は平均 0.195/255**
しかない（`tools/ablur_effect.py` で実測。参照実装との差 9.34/255 の 2%）。
ぼかすにはセル全体 65536 画素をなめる 1 パスが要るので割に合わない。

### 1 つの枠に奥層と手前層が混ざる

層の選択は**表の語を増やさず** 23 語目の bit1 に入れた（bit0 は premul）。

下の色は**両方の層から同じ番地を読んでおき、スロットごとに選り分ける**。
先読みの拍には `cell_front` がまだ前の枠の値なので、それでは選べない。

### ★ 段5d-5 で踏んだ 2 つ

**1. 表を 271 個にしたら LUT が 99.99% になって配置できなかった**

`pdriver` が 24 語を**同時に**引いていた。64 個（1536 語）なら収まったが、
271 個（6504 語）だと**巨大なマルチプレクサ**になり LUT が **+30769**。

```
ERROR: [Place 30-487] ... 9933 CLBs are available,
       however, the unplaced instances require 10088 CLBs
```

BRAM は読み口が 2 本しかないので 24 本同時には引けない。
**1 語ずつ 24 クロックかけて読む**形に直した。1 個あたり 42 クロックで、
1 枠 1600 クロックに対して無視できる。

```
LUT  117108 (99.99%) → 71747 (61.3%)    BRAM は +5.5 個だけ
```

直す途中で 2 回踏んだ。どちらも**組み合わせで出すべき信号をレジスタにした**:
- 読み出し番地をレジスタにして 1 拍ずれた
- `rd_v` をレジスタにして**最初の語だけ取りこぼした**（`p_type` だけ x になる）

**2. ★★ PL の描画を PS の流し込みが上書きしていた（段5d-6）**

実機で「きれいに出るが模様が速く動いて周期的に出たり消えたりする」、
手前層を透明にクリアしたら「操作画面は出るが**絵が出ない**」となった。

シリアルの一行で確定した。

```
油の地を入れ、手前層を透明にした (65536 語 x 2、4 フレームぶん)
```

**流し込みに 67ms（4 フレーム）かかる。** 一方 `pdriver` は起動後
`warm` = 4095 クロック = **55μs** で描き始める。PL は 10ms で 271 個を
描き終えるので、**PL が先に全部描き、そのあと PS が上書きしていた。**

| | 奥層 | 手前層 | 見えていたもの |
|---|---|---|---|
| 段5d-1〜5d-4 | PL が描く→**PS が上書き** | PS が本物を書く | 手前層だけ |
| 段5d-5 | PL が描く→**PS が上書き** | PL が描く→**PS が透明で上書き** | **何も残らない** |

★ **段5d-1〜5d-4 で「PL が描いた奥層のピース」は実は見えていなかった。**
段5d-1 以降ずっと「違いが分からない」と言われ続けたのはこれが理由。
段5c で見えたのは、まだセルを焼き込んでいて流し込みが無かったから。

直し方: **AXI に `0x1A0 DRAW_REQ` を足し、PS が流し込みを終えてから
1 回書く。** `pdriver` は `warm` カウンタの代わりにこれを待つ。
合成なしでは直せない（PL は 55μs で描き始め、PS からは止められない）。

### 資源と時間

```

FF   54096 (23.1%) → 54589 (23.3%)
BRAM 41.5  (28.8%) → 47    (32.6%)   表を LUT から BRAM へ移したぶん
URAM 32    (50.0%) → 32    (50.0%)
DSP  731   (58.6%) → 731   (58.6%)
```

## 段5d-7 — 二重バッファ・AXI でピースを渡す

奥層・手前層を 2 面ずつ URAM に置き（`rtl/cell_dbuf.v`）、描く面と映す面を分けた。
PS は毎フレーム「ピースの表」(271 個 x 24 語) を AXI で書いて `DRAW_REQ` を書くだけ。
起動時の油の地の流し込み (67ms) は無くなった。油の地は PL の ROM から写す。

### 実機（2026-10-17）

```
表の自己検査: 6504 語中 0 語不一致
描き直し 150 回 / 300 フレーム
```

ピースがその場で回り、ちらつきは無い。描き直しが 2 フレームに 1 回 (30Hz) なのは、
PS が「入れ替え済み」を見るのが入れ替えの次のループになるため（設計どおり）。

### 資源と時間

```
LUT  71854 (61.35%)   FF 54815 (23.40%)
BRAM 66.5  (46.18%)   URAM 64 (100%)   DSP 730 (58.49%)
WNS  +2.441ns         合成 43 分 36 秒
```

### ★ 実機で AXI を固めたら電源ケーブルを抜く

PL の AXI が応答しない状態で CPU が固まると、そのあと基板と JTAG が壊れた状態になり、
**実績のある Pong すら FSBL・psu_init で止まる**（`AP transaction timeout`、
`EDITR not ready`、`Memory read error at 0xFE20C200`）。
Vitis を閉じ、hw_server を終わらせ、**電源ケーブルを抜いて 1 分待つ**と直る。
この状態のまま設計を疑わないこと。

## 段6b — 表の上限 2048 個・表の書き込み口を AXI クロックに

段6 では、PS が表を 1 語書くたびに AXI 側から映像クロック側へ受け渡していた。
速く書くと取りこぼして描き直しが止まるので、1 語ごとに間隔を空けていた（表 598 個で 7.3ms）。

段6b では pdriver の表の RAM を **2 クロックの BRAM**（書き込み = AXI クロック、
読み出し = 映像クロック）にした。受け渡しの回路が要らなくなり、間隔空けも外した。
表の上限 (`MAXP`) は 645 → 2048 個。

### 実機（2026-10-19）

```
表の自己検査: 14352 語中 0 語不一致
描き直し 150 回 / 300 フレーム  物理 最大 5190〜8209 us  表 最大 1147〜1183 us
```

2 分半、描き直しは止まらなかった。表の書き込みは 7.3ms → **1.17ms**。
物理演算は時間がたつと 5 → 8ms に増える（ピースが寄り集まり、同じマス目の組が増えるため）。
ピースを増やすなら物理演算の高速化が先。

★ `vitis_src/main.c` は段6b の RTL が前提（間隔空けを外した）。段5d-7 / 段6 の bit では動かさないこと。

### 資源と時間

```
LUT  71745 (61.26%)   FF 54764 (23.38%)
BRAM 88.5  (61.46%)   URAM 64 (100%)   DSP 730 (58.49%)
WNS  +2.481ns         合成 47 分 49 秒
```

### ピースを 2038 個に（2026-10-19）

| 手を入れたところ | 結果（2038 個） |
|---|---|
| ビルドの最適化 `-O0` → `-O2`（★ Vitis の `kaleido_app/src/UserConfig.cmake`。リポジトリの外） | 598 個で物理演算 7.5 → 3.3ms、描き直し 30 → 60Hz |
| 押し合いを、当たり判定の値だけマス目順に float で詰めた配列に書き直す。隣のマスは片側半分だけ | 押し合い 16 → 8ms（毎フレーム約 32 万組） |
| 描き直しの依頼を物理演算の**前**に移す | 描き直し 20 → 30Hz（PL の描き直しに 30ms 余りかかるため） |

2038 個: 物理演算 最大約 10ms・表の書き込み 2.5ms・描き直し 30Hz（150 回 / 300 フレーム）。
シリアルに「内訳 平均: 移動・押し合い・壁・組・重なり」を出すようにした。
上限は 2048 個（`pdriver` の `MAXP`）。超えるには再合成が要り、描き直しは 20Hz に落ちる見込み。

### 色の組み合わせ・細かい粒・ラメのきらめき（2026-10-20）

- `c` キーで色の組み合わせを 6 通りに切り替える（ORIGINAL / JEWEL / RAINBOW / PASTEL / WARM / BLUE）。
  表に入る色を PS で差し替えるだけなので合成は要らない。ビーズには明るい色の並びを別に持たせた
  （宝石色をそのまま当てたら「細かな粒が無い」と言われた。濃い色の小さい粒は暗い地に沈む）。
- 小ビーズを半径 0.0025〜0.00625 から 0.008〜0.0125 に戻した。半分にした大きさは 1 画素より小さく、
  α の最大が平均 0.17 で 15% しか見えていなかった（`tools/grain_audit.py`）。
- 構成を 色ガラス 120 / ビーズ 250 / 小ビーズ 500（淡い色）/ 天然石 100 / ラメ 1050 にした（合計 2038）。
  細かくすると覆われる面積が減って暗い地が増える（`tools/mix_variants.py` で 49.8% → 43.3%）。
- ラメに時刻を渡すようにした（表の 18 語目。段6 までは 0 で、時間によるきらめきが止まっていた）。
  速さは参照実装の 2.5 倍（`GLIT_SPEED`）。描き直しは 30Hz のまま、物理演算は最大 11.9ms。

**分かった限界**: セル 1 画素は画面 0.88 画素（大きさ 100）。模様を大きくすると 1 画素が拡大され、
細かい粒は点でなく塊になる（大きさ 50 以下だと点に見える）。セルを 512 にするのは URAM（100%）と
描き直しの時間（4 倍）で無理。次の候補は、折り返し後の細かい座標から画面の画素で光る点を計算する
「きらめき層」（要合成。資源とタイミングの見込みを先に調べる）。

見比べの道具: `tools/look_variants.py`（重ね方の候補）、`tools/mix_variants.py`（構成の候補）、
`tools/grain_audit.py`（粒がどれだけ見えるか）。

## 段7 — きらめき層（2026-10-21 実機）

模様を大きくするとセル 1 画素が拡大され、細かい粒が点でなく塊になる（段6b の「分かった限界」）。
そこで、折り返し後の細かい座標 (cx, cy) から**画面の画素の細かさで光る点**を作り、α 合成の後に足す。

- `rtl/sparkle.v`（10 段）: 座標を格子に切り、格子ごとのハッシュで点の有無・位置・位相・速さ・色を決め、
  時刻で明滅させる。正解は `tools/sparkle_fx.py`。`python tools/tb_sparkle_check.py` で 20000 画素
  （本物の折り返し座標と範囲の端）を照合して**不一致 0**。
- AXI（`rtl/kaleido_axi_slave.v` のコメントが正）:
  - `0x1B0 SPK_CTRL`: bit0 = 出す、bit3:1 = 格子 2^lv マス、bit11:4 = 点がある割合 /256
  - `0x1C0 SPK_K`: (1 マスの画面画素 / 点の半径)^2、Q8
  - `0x1D0 SPK_GAIN`: bit7:0 = いつもの明るさ、bit15:8 = キラッと光るとき（128 = 1.0）
  - `0x1E0 SPK_TIME`: 時刻（256 で 1 周）。PS が毎フレーム進める
- `scope_pipe` の `out_cx` から 10 クロックで出る。α 合成の出力より 5 クロック遅いので、
  色の流れを `SPK_D = 5` 待たせて揃えた。**TOTAL_LAT 205 → 210**。
- main.c: 大きさ (zoom) から格子の細かさと点の大きさを決める。

資源: 合成 46 分・WNS +2.581ns・LUT 61.95%・DSP 59.1%・URAM 100%。
PS の設定は変えていないので psu_init はそのまま。

## 段7b — きらめき層の色を PS から・配色エディタ（2026-10-22 実機）

### 配色エディタ（合成不要）

- SD の `KPAL1〜4.TXT` に保存・読み込み（上の「操作」）。

### きらめき層の色（要合成）
段7 では点の色が `sparkle.v` に直書き（白・金・淡い青）で、「一番小さい粒の色が変わらない」と言われた。

- 色の番号を 4bit にし、AXI `0x1F0〜0x2E0`（`SPK_COL0〜15`、24bit RGB）の 16 色の表から P9 で引く。
  COMMIT のときフレーム先頭で映像側へ移す。初期値は白・白・金・淡い青の繰り返し。
- 試験では 16 色すべて違う表にして、表の引き方の間違いも見つける。20000 画素で不一致 0。
- エディタに SPARK を足した。8 色を割合で 16 個の置き場へ振り分ける（端数は余りの大きい順）。
  SPARK のときだけ `u j` 量 / `i k` 明るさ / `o l` 大きさ。SD には `SPARK` と `SPKPARAM` の行。
  SPARK を選ぶと色の表を黒にして点滅させる。

資源: 合成 50 分・WNS +2.776ns・LUT 62.15%・DSP 59.1%・URAM 100%。

## 段8a — 物理演算の高速化（2026-10-24 実機、ソフトだけ）

ピースを増やす前に、PS の物理演算（2038 個）を縮めた。各段とも起動から約 70 秒、安定したあとの値
（`SHOW_STATS` を 1 にして測る）。

| | 元 (16x16) | マス 23x23 | マス 32x32 + 大を別に | + 移動を単精度 |
|---|---|---|---|---|
| 調べた組 / フレーム | 約 41 万 | 約 23 万 | 約 14 万 | 約 14 万 |
| 押し合い 平均 | 9.6ms | 6.2ms | 4.4ms | 4.4ms |
| 移動 平均 | 1.7ms | 1.7ms | 1.7ms | 1.09ms |
| 物理 最大 | 11.7ms | 8.2ms | 6.4ms | **5.8ms** |
| 重なった組 | 約 10,500 | 約 10,500 | 約 10,600 | 約 10,500 |

- **マスが粗すぎた**: 一辺は「cr の最大の 2 倍」= 0.084 あれば足りるのに、16 分割固定で 0.125 だった。
  `tools/cr_stats.py` で cr の分布を数えて分かった（当たり判定あり 988 個、cr 0.008〜0.042）。
- **大を別に**: マスを 32x32（一辺 0.0625）にし、入らない cr > 0.03125 の 48 個（色ガラスなど）を外した。
  大は「大の cr + 小の cr の最大」までにかかるマス（前後 2 マスまで）の小と、大どうしは全部の組を調べる。
  取りこぼしは無い（重なった組の数が変わらない）。
- **移動を単精度**: `sinf` `cosf` と単精度の乱数。時刻の位相は倍精度で 2π に折り返してから渡す。
  状態 `sp[]` は倍精度のまま。

描き直しは 30Hz のまま（PL の描き直しに約 30ms かかるため）。空いた時間はピースを増やすのに使う。
上限 2048 個（`pdriver` の `MAXP`）を超えるには再合成が要る。
